# MQTT у Docker foundation

Підключення потребує TLS 1.2+ з перевіркою DNS-імені брокера та індивідуальним клієнтським сертифікатом. Виділений CA видає сертифікати пристроям після перевірки володіння оператором. CN пристрою має дорівнювати зареєстрованому UUID у канонічному нижньому регістрі. CN `edusense-worker` зарезервований для Worker. Ключі клієнтів залишаються у власників. Список відкликаних сертифікатів встановлюється оператором; після оновлення CRL потрібен контрольований перезапуск брокера для завершення старих з’єднань.

Пристрій публікує QoS 1 без retain у `edusense/v1/devices/{uuid}/telemetry` та `edusense/v1/devices/{uuid}/state`. ACL прив’язує публікацію до CN. Worker читає лише ці два типи топіків, а школу визначає за реєстром PostgreSQL. Payload телеметрії містить `schema_version: 1`, UUID `message_id` і масив `metrics` з полями `name`, `value`, `unit`. Доступні temperature/Cel, humidity/%, co2/ppm та gas_adc/count. Повтор пари ідентифікаторів пристрою й події з тією ж метрикою не створює додатковий запис. Повідомлення стану містить `schema_version: 1` та `status` зі значенням `online` чи `offline`. Надсилайте heartbeat кожні 30 секунд і використовуйте offline як Last Will. Через 90 секунд без повідомлень API показує offline.

ESP8266-скетч використовує старі топіки й спільні паролі. Він потребує окремого переходу на новий контракт. Цей етап охоплює серверний прийом телеметрії; команди, OTA, Gateway та аварійні сценарії залишаються поза серверним контрактом.

Щоб відкликати пристрій, оператор вимикає ідентичність через `DELETE /api/schools/{school_id}/devices/{uuid}` і додає сертифікат до CRL. Перша дія зупиняє запис телеметрії та зберігає історію. Оновлення CRL і перезапуск закривають доступ на рівні брокера.
