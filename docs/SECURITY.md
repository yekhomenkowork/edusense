# Безпека Docker foundation

У вихідному репозиторії API шкіл і моніторинг Docker не перевіряли доступ, API міг повертати поле спільного MQTT-пароля, а Compose передавав йому Docker socket. Broker використовував незахищений транспорт і звертався до маршрутів авторизації, відсутніх в активному API. Worker не міг записати повідомлення у чинну модель.

У гілці Docker foundation запити перевіряють серверну сесію й членство. Право адміністратора платформи потребує одноразового TOTP-коду; конфігурація підтримує один такий обліковий запис. Сесії зберігаються за хешем, діють вісім годин і відкликаються через API. Старі bcrypt-хеші оновлюються після успішного входу. Nginx обмежує частоту входу, а захищена діагностика повертає стан БД. Доступ до логів і контейнерів через веб-API вилучено.

PostgreSQL використовує окремі ролі для міграцій, застосунку та резервного копіювання. Роль застосунку спільна для API та Worker. Ізоляція забезпечується запитами застосунку, членствами та складеним FK телеметрії. RLS не впроваджено. Docker не передає сервісам сокет хоста. PostgreSQL починає роботу зі штатним entrypoint, якому потрібні вузькі capabilities для підготовки каталогу й переходу на користувача postgres. API та Worker працюють як UID 10001, Nginx як 101, Mosquitto як 1883. Опубліковані порти обмежено HTTPS та MQTT mTLS. Публічне відкриття MQTT потребує окремого рішення оператора.

Старі тестові значення й файл паролів видалені з нового дерева. Старі коміти збережено, тому історію слід вважати потенційним джерелом витоку. Секрети, які могли використовуватися в живому середовищі, потребують ротації його власником. Під час цієї роботи історія не очищалася, а живі секрети й ресурси не перевірялися.

Шкільні дзвінки, тривога й відбій, індикація затвердженого маршруту, базова діагностика й критичні оновлення залишаються безкоштовними за продуктовими вимогами. API `GET /api/schools/{school_id}/capabilities` перелічує ці права після перевірки членства, незалежно від тарифу. Локальні сценарії потребують Gateway і апаратної валідації.
