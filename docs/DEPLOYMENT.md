# Розгортання EduSense

## Чистий запуск

Потрібні Git, Docker Engine або Docker Desktop з Linux-контейнерами, Docker Compose v2 із підтримкою `up --wait` для перевірок, мережа, DNS і підготовлені TLS-матеріали. Усі серверні пакети встановлюються під час збірки образів.

1. Клонуйте репозиторій і відкрийте його корінь. Скопіюйте `.env.example` у `.env`. У PowerShell використовуйте `Copy-Item .env.example .env`.
2. Вкажіть унікальний `COMPOSE_PROJECT_NAME` для нової інсталяції, ім’я БД, окремі ролі, пошту адміністратора, шляхи до файлів, порти й публічний ключ age одержувача бекапів.
3. Створіть файли нижче. Для нової БД згенеруйте три різні випадкові паролі щонайменше по 24 символи та пароль адміністратора щонайменше на 16 символів. Для наявного тому використовуйте чинні ім’я БД, роль власника і її пароль. Зміна файлу пароля власника не змінює пароль у наявному PostgreSQL.
4. Виконайте `docker compose up -d --build`. Перевірте `docker compose ps -a`. Міграція завершується з кодом 0, API, Nginx, Mosquitto й Worker переходять у healthy. Стан резервного копіювання перевіряється після першого дампа. Причину зупинки шукайте в `docker compose logs migrate backend mqtt_worker mosquitto backup`.
5. Відкрийте HTTPS-адресу з іменем із сертифіката. Увійдіть поштою, початковим паролем і TOTP-кодом із застосунку-автентифікатора.

| Каталог | Файли та призначення |
| --- | --- |
| `SECRETS_DIR` | `db-owner`, `db-app`, `db-backup`, `admin-password`, `admin-totp`, `backup-offhost-auth`. Файл `admin-totp` містить випадковий Base32-секрет, щонайменше 32 знаки, без padding. Адміністратор імпортує його в автентифікатор захищеним каналом. У `backup-offhost-auth` запишіть заголовок `Authorization` для сховища або створіть порожній файл. |
| `WEB_PKI_DIR` | `server.crt` із ланцюжком HTTPS та `server.key`. DNS-ім’я користувачів має бути в SAN. |
| `MQTT_SERVER_PKI_DIR` | `server.crt`, `server.key`, `ca.crt` і чинний `clients.crl`, навіть якщо відкликань ще немає. SAN сервера включає `mosquitto` для Worker і DNS-ім’я для зовнішніх клієнтів. |
| `MQTT_WORKER_PKI_DIR` | `ca.crt` для перевірки брокера та `worker.crt`, `worker.key` для ідентичності `edusense-worker`. |

У Compose файли секретів монтуються зі своїми правами доступу. Дозвольте читання лише власнику та процесам, яким файл потрібен. На Linux врахуйте UID 10001 для API/міграції, UID 101 для Nginx, UID 1883 для Mosquitto і UID postgres у відповідному Alpine-образі для бекапу. Docker Desktop має підтвердити читання bind mounts у своїй Linux VM. Закриті ключі CA та age зберігаються окремо від сервера. Файли конфігурації й секретів слід тримати під окремим контролем доступу; ці каталоги не входять до Git і build context.

API, БД та Worker не публікують портів. HTTPS слухає 443 за замовчуванням. MQTT слухає 8883 на loopback хоста. Для зовнішніх клієнтів оператор явно задає `MQTT_BIND_ADDRESS` і обмежує доступ мережевими правилами. Деталі клієнтів наведено в [MQTT-контракті](DEVICE_PROTOCOL.md).

## Наявні дані та оновлення

Збережіть ім’я Compose-проєкту, яким створено попередній том PostgreSQL, і підготуйте перевірену резервну копію. Спочатку проганяйте оновлення на копії у відокремленому середовищі. Одноразовий сервіс бере транзакційний advisory lock, виконує Alembic, готує ролі й додає адміністратора за відсутності. Існуючий пароль адміністратора цей крок не скидає. Для legacy-інсталяції задайте нову адресу bootstrap-адміністратора або окремо перевірте чинний пароль наявного привілейованого акаунта.

Поточна ревізія доповнює відомі варіанти `schools` і `users`, додає членства й нові таблиці пристроїв та телеметрії. Вона зберігає старі записи, інвентар і телеметрію. Старі записи телеметрії залишаються в історичних таблицях, поки оператор не підтвердить відповідність ідентичностей. Старий файл стану брокера зберігається, а нова конфігурація використовує інше ім’я файлу. Зупиніть оновлення, якщо ревізія повідомляє про невідомий варіант схеми або недостатні права.

## Резервні копії й відновлення

Сервіс `backup` виконує `pg_dump` у custom format, перевіряє читання архіву через `pg_restore`, шифрує age та публікує готовий файл атомарно у непублічному томі `backup_data`. Інтервал за замовчуванням — 24 години, строк зберігання — 14 днів. Ротація починається після появи перевіреної нової копії. Обмеження tmpfs/пам’яті мають уміщати найбільший очікуваний дамп; оператор має перевірити це на своїх обсягах. Сервіс повідомляє про невдачу через логи й unhealthy. Підключіть зовнішнє оповіщення і виміряйте реальні RPO/RTO перед пілотом.

`BACKUP_OFFHOST_URL` підтримує HTTPS PUT шифрованого архіву. Використовуйте виділене сховище з мережевим обмеженням доступу та власними правилами retention. Автоматизація не звертається до сторонніх хостових файлів. Конфігурацію, CA, CRL, секрети й ключ age резервуйте окремим схваленим процесом.

На ізольованому стенді [процедура відновлення](TESTING.md) створює окрему БД, розшифровує архів і перевіряє контрольний запис. Для ручного відновлення підготуйте окрему інсталяцію з новим томом PostgreSQL і необхідними ідентичностями. У довіреному контейнері з age та клієнтом PostgreSQL виконайте `age -d -i /fixture/backup-identity.txt -o /tmp/restore.dump <archive>` і `pg_restore --no-owner --no-acl --exit-on-error --dbname=<нова_БД> /tmp/restore.dump`. Звірте контрольні вибірки, відновіть права, виконайте пробний запуск і лише після погодження перемикайте трафік. Паролі DB-ролей і ACL потрібні окремо від архіву.

Якщо оновлення зупинилося, збережіть томи, попередні образи й логи. Повернення образів припустиме після перевірки сумісності схеми. Якщо схема несумісна, відновіть перевірену копію в новий том і перевірте її до будь-якого перемикання. Автоматичного downgrade з видаленням колонок або таблиць немає.
